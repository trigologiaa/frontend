# US-00 — Tooling and local quality gates

**As a** developer, **I want** a JavaScript React app skeleton where formatting, linting, tests and
commit messages are checked automatically before anything enters the repository, **so that** every
later story starts from a clean, tested base and no untested production code can be committed.

This is a technical (enabler) story. It has no visitor-facing behavior except one: the app renders
its name. Its critical point is that the **quality gates exist before the first feature**, so the
first line of production code already goes through them.

Requirement: prerequisite of every pre-delivery requirement (see the [index](README.md)).

Depends on: nothing (it is the first story).

## Scope

Included:

- A Vite + React + JavaScript project managed with **pnpm**, on the latest Node LTS (pinned).
- **Biome** for formatting and linting (instead of ESLint + Prettier).
- **Vitest** + **React Testing Library** + **user-event** + **jest-dom**, with coverage thresholds.
- **Knip** to detect unused files, exports and dependencies.
- **Husky** hooks: `pre-commit` (Biome on staged files through **lint-staged**, plus the tests),
  `commit-msg` (**Commitlint**) and `pre-push` (the full `verify` script).
- **Commitizen** as an optional guided way to write Conventional Commits.
- A single `verify` script that runs everything the pipeline will run (US-01 just calls it).
- The first TDD cycle: the app renders its name.

Not included:

- The remote pipeline (GitHub Actions), branch protection and the deployment: **US-01**.
- Routing, layout and any real page: **US-02** onwards.
- MSW, Playwright and Storybook: they are installed by the story that needs them (MSW in US-07,
  Playwright in US-15). Storybook is optional and outside the pre-delivery.

## Acceptance scenarios

These scenarios are written in [Gherkin](https://cucumber.io/docs/gherkin/). Only the first one is an
automated test (Vitest + RTL). The rest describe tooling behavior and are verified by running the
command described in the implementation guide (it is how you prove the gate really blocks).

```gherkin
Feature: Tooling and local quality gates
  As a developer
  I want automatic checks before code enters the repository
  So that every later story starts from a clean, tested base

  Scenario: The app renders its name
    When I open the app
    Then I see the heading "Trigologia Dev"

  Scenario: Badly formatted code is fixed or rejected at commit time
    Given a staged file that Biome flags
    When I commit
    Then the commit is fixed automatically or rejected

  Scenario: A failing test blocks the commit
    Given a staged change that makes a test fail
    When I commit
    Then the commit is rejected

  Scenario: A non-conventional commit message is rejected
    When I commit with the message "changes"
    Then the commit is rejected with a Commitlint error

  Scenario: A failing check blocks the push
    Given a commit that makes "pnpm verify" fail
    When I push
    Then the push is rejected

  Scenario: Untested production code is detected
    Given a production file with a branch that no test executes
    When I run "pnpm test:coverage"
    Then the command fails because of the coverage threshold

  Scenario: Unused code is detected
    Given an exported function that nothing imports
    When I run "pnpm knip"
    Then the command fails and names the unused export
```

### Content

The only visible copy: the brand name **Trigologia Dev** (provisional: change it in one place when
the final name exists).

## Non-functional requirements

- **Reproducible environment:** Node version pinned (`.nvmrc` + `engines`), pnpm version pinned
  (`packageManager`), lockfile committed.
- **Fast feedback:** `pre-commit` runs only what is needed (lint-staged + unit tests, seconds);
  the slow checks (build, coverage, knip) run at `pre-push` and in the pipeline.
- **Nothing skipped silently:** `--no-verify` is forbidden by the workflow; the pipeline (US-01)
  re-runs every check, so skipping a hook only delays the failure.

## Decisions

- **pnpm** (not npm/yarn): fast, strict about dependencies, and `packageManager` pins the version.
- **Biome instead of ESLint + Prettier:** one tool, one config, much faster. Delete the ESLint files
  the Vite template generates.
- **Explicit imports from `vitest` (no globals):** `import { describe, it, expect } from 'vitest'`.
  It works the same in JS and TS and needs no extra type configuration.
- **Coverage thresholds at 100 %:** it is how "no production code without a test" becomes a rule
  the machine enforces. `src/main.jsx` (the bootstrap) and `test/` (outside `src/`) are excluded. If a
  threshold ever blocks something that is not worth testing, lower it consciously in a dedicated
  commit, never silently.
- **Scaffold is not "your" code:** the files generated by `pnpm create vite` are committed as a
  `chore:` and the template `App` is then replaced test-first. Configuration files are not
  production code and need no test.
- **First push goes straight to `main`:** it is the only time. From US-01 on, `main` is protected
  and everything arrives through a pull request.

## Definition of Done

- [ ] The smoke test passes and was seen failing first (red → green).
- [ ] Each gate of the scenarios above was **proved** to block (the guide shows how).
- [ ] `pnpm verify` is green locally.
- [ ] Commits follow Conventional Commits and each one is a green cycle.
- [ ] The repository is pushed to GitHub (`main`).
